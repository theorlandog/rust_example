# Packaging

Four native installers, one binary. Each platform is built by the script in its
own directory, and CI runs those same scripts — there is no separate CI-only
recipe that can drift from what you run locally.

| Platform | Output | Built by | Needs |
| --- | --- | --- | --- |
| Debian, Ubuntu | `rust-example_<version>-1_amd64.deb` | `packaging/linux/build-packages.sh` | `cargo-deb` |
| Fedora, RHEL, openSUSE | `rust-example-<version>-1.x86_64.rpm` | `packaging/linux/build-packages.sh` | `cargo-generate-rpm` |
| macOS | `rust-example-<version>-universal.pkg` | `packaging/macos/build-pkg.sh` | Xcode command line tools |
| Windows | `rust-example-<version>-x64.msi` | `packaging/windows/build-msi.ps1` | WiX Toolset v5 |

Everything lands in `dist/`.

## Where each package's contents are defined

The Linux packages are described declaratively in `Cargo.toml`, under
`[package.metadata.deb]` and `[package.metadata.generate-rpm]`: file lists,
permissions, the maintainer, the description, the dependency policy. There are
no `debian/` or `.spec` files to keep in step with the crate — the version and
description come from `[package]` itself.

macOS and Windows need real packaging toolchains, so their inputs are checked
in next to their scripts:

- `macos/distribution.xml` — the installer window: title, licence pane, and the
  architectures the payload supports.
- `windows/rust-example.wxs` — the WiX definition: install location, the
  Add/Remove Programs entry, upgrade behaviour, and the `PATH` entry.

## Building

```sh
# Linux (both packages)
cargo install cargo-deb cargo-generate-rpm
./packaging/linux/build-packages.sh

# macOS
./packaging/macos/build-pkg.sh

# Windows
dotnet tool install --global wix --version 5.*
wix extension add --global WixToolset.UI.wixext/5.*
./packaging/windows/build-msi.ps1
```

## Details worth knowing

**Completions are generated by the binary being packaged.** The Linux script
runs `rust-example completions <shell> --out-dir target/completions` and ships
the result, so the completion scripts can never describe a different set of
flags than the binary accepts. `cargo deb` will fail if you skip that step,
because the assets it is told to package will not exist — run the script rather
than `cargo deb` directly.

**glibc sets the compatibility floor on Linux.** A binary linked against glibc
2.39 will not start on a distribution shipping 2.35, so the release workflow
builds on the *oldest* supported runner (`ubuntu-22.04`) rather than the newest.
For packages that run anywhere, build against musl instead
(`rustup target add x86_64-unknown-linux-musl`) and pass `--target` through to
`cargo deb` and `cargo generate-rpm`.

**The macOS package installs a universal binary.** The script builds both
`aarch64-apple-darwin` and `x86_64-apple-darwin` and merges them with `lipo`, so
there is one download rather than two and no wrong choice for the user to make.

**Unsigned installers are second-class.** On macOS, Gatekeeper blocks an
unsigned `.pkg` downloaded from the internet. The script signs and notarises
when `MACOS_CODESIGN_IDENTITY`, `MACOS_INSTALLER_IDENTITY`, and
`MACOS_NOTARY_PROFILE` are set, and builds an unsigned package when they are
not, so a local build needs no Apple Developer account. Windows has the same
split: an unsigned `.msi` shows a SmartScreen warning. Add `signtool sign` to
`build-msi.ps1` when you have a certificate.

**`UpgradeCode` in the `.wxs` must never change.** It identifies the product
line, and it is how Windows knows that 0.3.0 replaces 0.2.0 rather than
installing beside it. Generate a fresh one (`uuidgen`) when you fork this
repository, then leave it alone forever.

**MSI versions are numeric only.** `0.3.0-rc.1` is not a valid
`ProductVersion`; the Windows script trims the pre-release suffix for the
installer and keeps the full version in the file name.

## Cross-compiling

These scripts build for the host architecture, which is why the release
workflow uses a native runner per platform. To add an architecture, build for
its target and pass the triple to the packagers:

```sh
rustup target add aarch64-unknown-linux-gnu
cargo build --release --target aarch64-unknown-linux-gnu
cargo deb --no-build --target aarch64-unknown-linux-gnu
cargo generate-rpm --target aarch64-unknown-linux-gnu
```

Both packagers rewrite the `target/release/...` asset paths to match. The
linker is the part that needs setting up — either install a cross toolchain and
point `CARGO_TARGET_<TRIPLE>_LINKER` at it, use [`cross`], or add a native
`ubuntu-24.04-arm` job to the release workflow, which needs no cross setup at
all. Completions are architecture-independent, so a cross build can reuse the
ones generated by a host build.

[`cross`]: https://github.com/cross-rs/cross

## Adding a man page

`clap_mangen` turns the same `clap` definition into troff, the way
`clap_complete` turns it into completion scripts. Add it as a build dependency,
generate `rust-example.1` alongside the completions, and add one line per
package to the asset lists in `Cargo.toml`
(`/usr/share/man/man1/rust-example.1.gz` for both Linux packages).
